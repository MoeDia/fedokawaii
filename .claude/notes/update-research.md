# Update research — T43 (round 27): sources for a bulletproof one-button updater

The design (T44, `.claude/notes/update-design.md`) cites this file line by line. Each source: its link,
what it is, and the one thing it taught us. Six batches, one subagent each, merged by the main agent;
the synthesis (failure modes seen in practice, ranked, each with its countermeasure) goes at the top
once the batches are in.

This PC (checked 1 Nov 2026): Fedora 44 (SUPPORT_END 2027-05-19), dnf5 5.4.6, snapper 0.13.0 (config
`root` on /), grub2 2.12-66 + grub-btrfs 4.14, btrfs-progs 7.1, systemd 259.10. Disk: / = Btrfs
subvolume `root` (zstd:1, noatime) — **/home is inside it** (no own subvolume; only
home/dia/Downloads and home/dia/VM are), /boot = XFS on its own partition (outside every snapshot),
/boot/efi = vfat.

## Synthesis — the failure modes seen in practice

Ranked by how often the sources show it × how much it costs the person (F frequency, D damage:
3 high · 2 medium · 1 low; rank = F × D). Each: the countermeasure, who does it that way, a source.
"Bn #k" = batch n's design bullet k below (its URLs there).

What the ranking says for our design (update-design.md): the top four are about the boot (kernels,
/boot, interrupted transactions, space) — the button's strength must be there first; the
candidate-first flow answers 3, 10, 15, 20, 23; the layout answers 2, 6, 7, 19; probation answers
1, 17, 18.

## Batch 1 — official documentation (dnf5, rpm, snapper, grub-btrfs, btrfs, systemd, Fedora, fwupd, greenboot)

Checked 1 Nov 2026, 86 sources. "(via search)" = the page was confirmed by a web search that returned its text, because the host
refused a direct fetch (docs.fedoraproject.org is behind the Anubis bot wall; gnu.org answered HTTP 429). snapper.io fails TLS
validation from here, so snapper's man pages are cited from openSUSE's own manpages host (the upstream). Facts about "this PC" were
read from the installed system (rpm, unit files, /proc/cmdline), read-only.

- https://dnf5.readthedocs.io/en/latest/commands/offline.8.html — dnf5 offline command — State sits in /usr/lib/sysimage/libdnf5/offline (inside the root snapshot); `log --number=-1` shows the last attempt; `reboot --poweroff` still reboots if the transaction failed.
- https://dnf5.readthedocs.io/en/latest/commands/system-upgrade.8.html — dnf5 system-upgrade command — Subcommands download/reboot/clean/log; --releasever required; default acts like distro-sync (may downgrade; --no-downgrade changes that); the page covers no backup, third-party-repo or failure handling.
- https://dnf5.readthedocs.io/en/latest/libdnf5_plugins/actions.8.html — libdnf5 actions plugin — pre_transaction/post_transaction hooks run any command; raise_error=1 turns a failing hook into an exception (default only logs); the page's own example emulates the DNF4 snapper plugin.
- https://dnf5.readthedocs.io/en/latest/commands/versionlock.8.html — dnf5 versionlock command — Built-in /etc/dnf/versionlock.toml with name globs and epoch/evr/arch conditions (AND within an entry, OR across entries); add/exclude/delete/clear; ignored by non-transactional queries.
- https://dnf5.readthedocs.io/en/latest/commands/history.8.html — dnf5 history command — list/info/undo/redo/rollback/store by transaction id (last-1, 4..8); rollback reverts all later transactions; flags --ignore-extras/--ignore-installed/--skip-unavailable; old-package availability is not promised.
- https://dnf5.readthedocs.io/en/latest/dnf5.conf.5.html — dnf5.conf(5) — installonly_limit default 3 (minimum 2), protect_running_kernel default true; tsflags=test checks the transaction (downloads, keys, file conflicts) without executing it; minrate/timeout abort stalled downloads.
- https://dnf5.readthedocs.io/en/latest/dnf5.8.html — dnf5 main man page — Only exit codes 0, 1 and 2 are documented; -C/--cacheonly never refreshes metadata; --best makes upgrades fail with the reason instead of skipping broken packages.
- https://dnf5.readthedocs.io/en/latest/commands/check-upgrade.8.html — dnf5 check-upgrade — Exit 100 means updates are available, 0 means none: the cheap "anything to do?" probe (the page does not say whether it refreshes metadata).
- https://dnf5.readthedocs.io/en/latest/commands/upgrade.8.html — dnf5 upgrade command — `--offline` stores the transaction, `--downloadonly`/`--destdir` only fetch, `--security`/`--bugfix` filter, `--skip-unavailable` skips what cannot be upgraded; there is no `--skip-broken`.
- https://dnf5.readthedocs.io/en/latest/commands/distro-sync.8.html — dnf5 distro-sync command — Upgrades, downgrades or keeps packages to match the repos; `--store` writes the transaction for review and replay; `--downloadonly` resolves and fetches without applying.
- https://dnf5.readthedocs.io/en/latest/changes_from_dnf4.7.html — Changes between DNF and DNF5 — system-upgrade is built in; unmatched arguments now fail unless --skip-unavailable; `best` defaults to true; cache moved to /var/cache/libdnf5; dnf-automatic became a plugin.
- https://dnf5.readthedocs.io/en/latest/dnf5_plugins/needs_restarting.8.html — dnf5 needs-restarting — Exits 1 when a reboot is recommended (kernel, systemd, listed core packages); extra packages go in /etc/dnf/suggest-reboot.d/*.conf; the DNF4 plugin directory is ignored.
- https://dnf5.readthedocs.io/en/latest/dnf5_plugins/automatic.8.html — dnf5 automatic command — dnf5-automatic.timer plus /etc/dnf/automatic.conf (download_updates, apply_updates, reboot never/when-changed/when-needed); no exit codes documented; unused here because the owner wants no background updates.
- https://github.com/rpm-software-management/dnf5/releases — dnf5 GitHub releases — 5.4.6.0 is current; 5.4.3.0 was published as "broken - do not use" yet added "invalidate offline transaction after successful online transaction"; 5.4.5.0 skips empty transactions.
- https://github.com/rpm-software-management/dnf5/releases/tag/5.4.4.0 — dnf5 5.4.4.0 release — Added the systemd inhibitor-lock plugin (libdnf5-plugin-systemd-inhibit), IPlugin2_2 cleanup hooks and an ABORT return for interaction callbacks.
- https://rpm.org/docs/latest/man/rpm.8 — rpm(8) 6.1.0 — Offers --test ("go through the motions"), --justdb and --noscripts but no rollback option; exit status is only 0 or non-zero.
- https://rpm.org/docs/latest/man/rpmdb.8 — rpmdb(8) — --rebuilddb rebuilds from package headers and discards unreadable ones; --verifydb is only low-level, `rpm -Va` is the meaningful health check; --exportdb/--importdb transport the DB.
- https://rpm.org/docs/latest/man/rpm-scriptlets.7 — rpm-scriptlets(7) — A failing %pre/%pretrans stops only that package, not the whole transaction; any non-zero scriptlet is reflected as an error in the transaction result code.
- https://rpm.org/docs/latest/man/rpm-plugin-systemd-inhibit.8 — rpm-plugin-systemd-inhibit(8) — Holds a block-mode idle:sleep:shutdown inhibitor for the whole transaction so a reboot request cannot interrupt it; advised on all systemd systems.
- https://fedoraproject.org/wiki/Changes/Sqlite_Rpmdb — Changes/Sqlite_Rpmdb (F33) — The sqlite rpmdb is transactional: a forcibly killed transaction no longer corrupts the database; BDB conversion ran through the rpmdb-rebuild service after upgrade.
- https://fedoraproject.org/wiki/Changes/RelocateRPMToUsr — Changes/RelocateRPMToUsr (F36) — The rpmdb lives in /usr/lib/sysimage/rpm so snapshots and rollback keep it consistent with /usr; DNF history stayed in /var until dnf5.
- https://www.fedoraproject.org/wiki/Changes/Enforcing_signature_checking_by_default — Changes/Enforcing_signature_checking_by_default (F45) — `%_pkgverify_level` goes from digest to all: unsigned or unverifiable RPMs are refused; repos with gpgcheck=0 are handled per package by dnf5 5.2.14 or newer.
- https://fedoraproject.org/wiki/Changes/RPM-6.1 — Changes/RPM-6.1 (F45) — Fedora 45 rebases to rpm 6.1 with "no intentional incompatibilities"; queries work during transactions again; contingency is reverting to 6.0 by Beta freeze.
- https://manpages.opensuse.org/Tumbleweed/snapper/snapper.8.en.html — snapper(8) 0.13.1 — rollback "creates two new snapshots and sets the default subvolume" (btrfs only, "properly configured system"); `create --command` wraps pre/post; undochange gives no consistency guarantee.
- https://manpages.opensuse.org/Tumbleweed/snapper/snapper-configs.5.en.html — snapper-configs(5) — Defaults NUMBER_CLEANUP=no, NUMBER_LIMIT=50, NUMBER_LIMIT_IMPORTANT=10 (counted separately), SPACE_LIMIT=0.5, FREE_LIMIT=0.2; space limits need quota (setup-quota).
- https://doc.opensuse.org/documentation/tumbleweed/snapper/ — Snapper and Btrfs (openSUSE docs) — Rollback means booting a read-only snapshot then `snapper rollback`; the layout expects snapshots directly under @/.snapshots (a health check flags others); /home is a separate subvolume, not snapshotted.
- https://github.com/openSUSE/snapper — openSUSE/snapper repository — "Manage filesystem snapshots and allow undo of system modifications"; ships a zypp plugin and PAM module but no dnf plugin; snapper.io failed TLS validation (certificate issued for github.com).
- https://github.com/Antynea/grub-btrfs — grub-btrfs README — Auto-detects a separate /boot; Fedora needs grub2-mkconfig and /boot/grub2 settings; read-only snapshot boot needs /var (or /var/log) on its own subvolume or the overlayfs hook.
- https://github.com/Antynea/grub-btrfs/blob/master/41_snapshots-btrfs — grub-btrfs 41_snapshots-btrfs — With a separate /boot (boot_separate) every snapshot entry uses the live /boot kernels and initramfs; only boot_bounded uses each snapshot's own /boot; no kernel found is an error (exit 0).
- https://github.com/Antynea/grub-btrfs/blob/master/initramfs/readme.md — grub-btrfs overlayfs hook (dracut) — dracut older than 109 has an overlayfs mount bug needing a hand-patched module copy; uses rd.live.overlay.* parameters; changes inside the booted snapshot vanish at reboot.
- https://github.com/Antynea/grub-btrfs/blob/master/config — grub-btrfs config — GRUB_BTRFS_LIMIT=50 entries; GRUB_BTRFS_ROOTFLAGS must not contain subvol/subvolid; extra snapshot kernel parameters allowed; Fedora must set GRUB_BTRFS_MKCONFIG=grub2-mkconfig and grub2-script-check.
- https://github.com/Antynea/grub-btrfs/blob/master/grub-btrfsd — grub-btrfsd — inotifywait on create/delete/unmount of the snapshot directory, waits 5 s, then regenerates the submenu; no lock or debounce, so bursts of snapshot events can be missed.
- https://github.com/dracut-ng/dracut-ng/blob/main/man/dracut.cmdline.7.adoc — dracut.cmdline(7) — rd.live.overlay* options are renamed rd.overlay* since dracut 110; rootflags, ro, rd.break and rd.shell are the rescue handles for a snapshot boot.
- https://btrfs.readthedocs.io/en/latest/Subvolumes.html — Btrfs subvolumes — Snapshots default to read-write; nested subvolumes are a barrier and not included; data that must survive rollbacks belongs in its own subvolume; a snapshot is not a backup.
- https://btrfs.readthedocs.io/en/latest/btrfs-subvolume.html — btrfs-subvolume(8) — set-default "takes action on next mount" and hides the top-level subvolume; delete without -c/-C may reappear after a crash; freed space returns asynchronously (subvolume sync waits).
- https://btrfs.readthedocs.io/en/latest/Scrub.html — Btrfs scrub — Recommended monthly; repair only from replicated profiles (a single profile just detects); status kept in /var/lib/btrfs; an interrupted scrub can resume after kernel 6.19.
- https://btrfs.readthedocs.io/en/latest/Balance.html — Btrfs balance — Very I/O-heavy and needs workspace or returns ENOSPC; `-dusage=0` (or small values) frees empty chunks cheaply; interrupted balances resume at mount unless skip_balance.
- https://btrfs.readthedocs.io/en/latest/Qgroups.html — Btrfs quota groups — Accounting "can slow down transaction commits ... especially ... as snapshots scale up"; simple quotas skip shared/exclusive tracking and suit immutable snapshots.
- https://btrfs.readthedocs.io/en/latest/btrfs-filesystem.html — btrfs-filesystem(8) — `usage` reports estimated free space and the global reserve; `df` is a debugging helper; defragment breaks reflinks of snapshots and can inflate space use.
- https://btrfs.readthedocs.io/en/latest/trouble-index.html — Btrfs troubleshooting (ENOSPC) — Exhausted metadata blocks new extents, inline files, reflinks and xattrs while deletion still works; balance itself needs temporary workspace.
- https://btrfs.readthedocs.io/en/latest/Administration.html — Btrfs administration — Only the first mounted subvolume's mount options take effect and subvol= may be given once; fstrim batches discards.
- https://btrfs.readthedocs.io/en/latest/Send-receive.html — Btrfs send/receive — Send needs a read-only subvolume, incremental sends take reference subvolumes, and every stream command carries a CRC32C: the basis of the backup-drive flow.
- https://btrfs.readthedocs.io/en/latest/Kernel-by-version.html — Btrfs changes by kernel version — squota since 6.7, discard=async default since 6.2, scrub resumable after suspend in 6.19; 7.1 and 7.2 fix flushoncommit and reflink deadlocks.
- https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/ — Automatic Boot Assessment — Counting lives in BLS entry file names (+LEFT-DONE) kept by systemd-boot; GRUB is not mentioned; other loaders must implement the rename logic and may reuse boot-complete.target.
- https://www.freedesktop.org/software/systemd/man/latest/systemd-bless-boot.service.html — systemd-bless-boot.service — Works from the LoaderBootCountPath EFI variable that the boot loader sets; good/bad/indeterminate rename the entry file; the page says nothing about GRUB.
- https://www.freedesktop.org/software/systemd/man/latest/systemd-boot-check-no-failures.service.html — systemd-boot-check-no-failures.service — Its only test is "no failed units"; disabled by default and "primarily useful ... as example" for finer checks ordered before boot-complete.target.
- https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html — systemd.special — boot-complete.target is a sync point outside the default transaction; system-update.target runs offline updates, and if the flag remains system-update-cleanup removes it and reboots.
- https://www.freedesktop.org/software/systemd/man/latest/systemd.offline-updates.html — systemd.offline-updates(7) — Remove the /system-update symlink as early as possible, always reboot afterwards (FailureAction=reboot), and on failure "revert to the old file system snapshot".
- https://www.freedesktop.org/software/systemd/man/latest/systemd-sysupdate.html — systemd-sysupdate (experimental) — A/B updating of images, partitions or files with InstancesMax bounding kept versions; rollback is not described and there is no package support: a design reference only.
- https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html — journald.conf — Storage=auto is persistent only if /var/log/journal exists; SystemMaxUse defaults to 10% and SystemKeepFree to 15% of the filesystem (capped at 4G); critical messages sync at once.
- https://systemd.io/INHIBITOR_LOCKS/ — Inhibitor Locks — Package-manager use case is a shutdown:idle block lock held during the work; "delay" exists only for sleep/shutdown; privileged users can still override block locks.
- https://www.freedesktop.org/software/systemd/man/latest/kernel-install.html — kernel-install(8) — Kernel image lives at /usr/lib/modules/KVER/vmlinuz; `add KVER IMAGE` recreates the BLS entry and initrd in $BOOT, `remove` deletes the entry directory; plugin exit 77 skips the rest.
- https://www.freedesktop.org/software/systemd/man/latest/os-release.html — os-release(5) — SUPPORT_END is an ISO date, "the first day on which support is not provided"; the page does not say which tools warn about it.
- https://uapi-group.org/specifications/specs/boot_loader_specification/ — UAPI Boot Loader Specification — Type #1 entries live in $BOOT/loader/entries; "bad" counted entries sort last; $BOOT is shared by all OS installs, so entries and kernels are not tied to one root.
- https://fedoraproject.org/wiki/Releases/45/ChangeSet — Fedora 45 ChangeSet — Lists RPM 6.1, enforcing signature checking, kmscon, restricted ptrace, OpenSSL 4.0 and GRUB-EFI for confidential computing; no entries for dnf5, systemd, Btrfs or SELinux.

### Batch 1: what matters for the design

Tags: [X] contradicts one of our assumptions (a)-(e); [OK] confirms one; the rest are new facts the design must absorb.

1. [X b] With a separate /boot, grub-btrfs boots a snapshot with the live /boot's kernels, not the snapshot's. In `boot_separate` mode kernels, initramfs and microcode are globbed once from the live /boot and reused for every snapshot entry (`boot_bounded`, per-snapshot /boot, applies only when /boot is inside the same Btrfs subvolume); entries add `rootflags=subvol=<snapshot>`; no kernel found prints "Kernels not found." and exits 0. A snapshot boots only if /boot still holds a kernel whose /usr/lib/modules/KVER exists in that snapshot. https://github.com/Antynea/grub-btrfs/blob/master/41_snapshots-btrfs
2. [X a] A root rollback does NOT keep /boot's kernels usable with installonly_limit=2. dnf5 keeps the 2 newest kernels (default 3, minimum 2; this PC sets 2 in /etc/dnf/libdnf5.conf.d/90-fedokawaii.conf) and kernel removal deletes their /boot files; a snapshot two or more kernel updates old then has no matching vmlinuz/initramfs on /boot (initramfs is built into /boot, never into a snapshot) and the newest kernel has no /usr/lib/modules/KVER in it. Every snapshot still carries /usr/lib/modules/KVER/vmlinuz (checked here), so the rollback step must run `kernel-install add KVER /usr/lib/modules/KVER/vmlinuz` (rebuilds BLS entry + initrd from the rolled-back root) before first boot, or kernel retention must follow snapshot retention. https://dnf5.readthedocs.io/en/latest/dnf5.conf.5.html https://www.freedesktop.org/software/systemd/man/latest/kernel-install.html
3. [X b] Read-only snapshot boot depends on a dracut hook that changes at exactly the release we are about to take. grub-btrfs needs /var (or /var/log) on its own subvolume or its overlayfs initramfs module; dracut < 109 has an overlayfs mount bug needing a hand-patched copy of module 70overlayfs (this PC: dracut 108-8, unless Fedora backported the fix: test in the VM); dracut 110 renamed `rd.live.overlay.*` to `rd.overlay.*` and F45 ships 111-4. Safer than the hook: boot a read-write clone of the chosen read-only snapshot. https://github.com/Antynea/grub-btrfs/blob/master/initramfs/readme.md https://github.com/dracut-ng/dracut-ng/blob/main/man/dracut.cmdline.7.adoc https://packages.fedoraproject.org/pkgs/dracut/dracut/fedora-45.html
4. [X, rollback mechanism] `snapper rollback` cannot work on this layout. It "creates two new snapshots and sets the default subvolume", and btrfs `set-default` "takes action on next mount"; but this PC pins root twice (`subvol=root` in fstab and `rootflags=subvol=root` on the kernel command line), and /.snapshots sits inside `root` (not a separate mount; snapper makes it a nested subvolume, and snapshots do not carry nested subvolumes). A rollback needs our own swap: a new read-write snapshot named in `rootflags=`/BLS options, with .snapshots moved to a top-level subvolume mounted at /.snapshots (the @/.snapshots layout snapper's health check expects). https://manpages.opensuse.org/Tumbleweed/snapper/snapper.8.en.html https://btrfs.readthedocs.io/en/latest/btrfs-subvolume.html https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://doc.opensuse.org/documentation/tumbleweed/snapper/
5. [OK c, with limits] dnf5 5.4.6 (identical in F45) has versionlock (/etc/dnf/versionlock.toml; name globs plus epoch/evr/arch conditions) and offline/system-upgrade built in; both ship with the dnf5 package set on this PC. History undo/rollback exist but do not promise old packages; only exit codes 0/1/2 are documented (check-upgrade adds 100); `upgrade` lost --skip-broken and unmatched specs now fail; `tsflags=test`, `--downloadonly`, `--store` and `system-upgrade download` are the no-change pre-flights; 5.4.3.0 was published as "broken - do not use", so pin the dnf5 build too. https://dnf5.readthedocs.io/en/latest/commands/versionlock.8.html https://dnf5.readthedocs.io/en/latest/dnf5.8.html https://github.com/rpm-software-management/dnf5/releases
6. Offline-upgrade mechanics. Its state lives in /usr/lib/sysimage/libdnf5/offline, inside the root subvolume, so a rollback restores whichever offline state the snapshot had: run `dnf5 offline clean` after any rollback. The installed unit has `Requires=sysinit.target dbus.socket` and `OnFailure=` a cleanup that deletes /system-update and reboots, matching systemd's rules (remove the flag early, always reboot, "revert to the old file system snapshot"); so a failed offline upgrade lands back in the old system and success must be judged by the resulting release, not by the absence of an error. https://www.freedesktop.org/software/systemd/man/latest/systemd.offline-updates.html https://dnf5.readthedocs.io/en/latest/commands/offline.8.html
7. [X d, partly] Fedora's grub2 has boot counting, but it is a kernel fallback, not a snapshot rollback. `08_fallback_counting` counts `boot_counter` down only while it is set and `boot_success=0`, and at 0/-1 sets `default=1` (the second entry: the next-older BLS kernel; on ostree "the rollback deployment"); `10_reset_boot_success` sets boot_success=0 on every boot, so userspace must set `boot_success=1` (Fedora: the user timer grub-boot-success.timer, 2 min into a session, via grub2-set-bootflag) and `boot_counter=N` ("both ... need to be set from userspace"); offline updates bump boot_indeterminate. GRUB's `fallback` fires only when commands of the chosen entry fail, not on OS-level failure. We need a system-level confirm unit ordered before boot-complete.target plus our own grub.d snippet to select a snapshot entry; grubenv is fine on our XFS /boot, whereas Fedora's Cloud change avoids grubenv features on a Btrfs /boot. https://github.com/rhboot/grub2/blob/fedora-46/util/grub.d/08_fallback_counting.in https://github.com/rhboot/grub2/blob/fedora-46/util/grub.d/10_reset_boot_success.in https://www.fedoraproject.org/wiki/Changes/CleanupGnomeHiddenBootMenuIntegration https://www.gnu.org/savannah-checkouts/gnu/grub/manual/grub/grub.html
8. Boot assessment elsewhere is not directly reusable. systemd's Automatic Boot Assessment is BLS-file-rename counting inside systemd-boot (GRUB is not mentioned; bless-boot needs the LoaderBootCountPath EFI variable); systemd-boot-check-no-failures only tests "no failed units" and is disabled by default; greenboot(-rs) gives the pattern (required.d/wanted.d checks before boot-complete.target, red.d/green.d, max attempts) but rolls back only through rpm-ostree/bootc. Reuse the pattern (our verify as a unit ordered before boot-complete.target), not the tools. https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/ https://www.freedesktop.org/software/systemd/man/latest/systemd-boot-check-no-failures.service.html https://github.com/fedora-iot/greenboot-rs
9. [X e, consequence] /home inside the root subvolume is rolled back with it, and so is /var (the persistent journal, capped at 500M here, and the logs of the failed attempt) plus everything under /home/dia except the nested Downloads and VM subvolumes: dotfiles, ~/repos and the .claude notes revert to the snapshot's state. Btrfs docs: give data that must survive rollbacks its own subvolume; Fedora's default layout has separate root and home subvolumes; openSUSE keeps /home out of snapshots. Before rollback ships, /home (and /var/log) must become their own subvolumes, and the update report must be copied out before any rollback. https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://fedoraproject.org/wiki/Changes/BtrfsByDefault https://doc.opensuse.org/documentation/tumbleweed/snapper/
10. Snapshot space is not managed by default. Snapper's defaults do no cleanup (NUMBER_CLEANUP=no, timeline off; NUMBER_LIMIT 50, important 10 counted separately); SPACE_LIMIT 0.5 / FREE_LIMIT 0.2 need quotas, and qgroups slow commits as snapshots multiply (squota, kernel 6.7 or newer, avoids shared/exclusive tracking). Metadata exhaustion gives ENOSPC while data space is free (deletion still works; balance needs workspace; start with `-dusage=0`); deleted snapshots free space asynchronously (`btrfs subvolume sync`, `delete -c`). The pre-flight must read `btrfs filesystem usage`, not df. https://manpages.opensuse.org/Tumbleweed/snapper/snapper-configs.5.en.html https://btrfs.readthedocs.io/en/latest/Qgroups.html https://btrfs.readthedocs.io/en/latest/trouble-index.html https://btrfs.readthedocs.io/en/latest/btrfs-filesystem.html
11. RPM gives no all-or-nothing transaction, so the snapshot is the only undo. A failing %pre stops only its package, any non-zero scriptlet turns the result into an error while the transaction goes on, and rpm.8 has no rollback option; the sqlite rpmdb at /usr/lib/sysimage/rpm survives a killed transaction and sits inside the snapshot, consistent with /usr; verify with `rpm -Va`, repair with `rpmdb --rebuilddb`; the rpm and libdnf5 systemd-inhibit plugins block shutdown during a transaction (a pulled plug still needs the snapshot). https://rpm.org/docs/latest/man/rpm-scriptlets.7 https://rpm.org/docs/latest/man/rpmdb.8 https://fedoraproject.org/wiki/Changes/Sqlite_Rpmdb https://rpm.org/docs/latest/man/rpm-plugin-systemd-inhibit.8
12. Bootloader files are outside every snapshot, and are about to move. The ESP (vfat) and /boot (XFS) are not Btrfs, so a root rollback never touches BLS entries, initramfs, grubenv or the shim/grub binaries; F44's BootLoaderUpdatesPhase1 stages shim/grub2 under /usr/lib/<pkg>/<arch> and copies them out in a posttrans step whose mechanism is still undefined (bootupd is the candidate), so after a rollback /usr may hold older bootloader files than the ESP: re-sync or tolerate. https://fedoraproject.org/wiki/Changes/BootLoaderUpdatesPhase1 https://packages.fedoraproject.org/pkgs/grub2/grub2-common/fedora-45.html
13. Fedora 45 ships Tuesday 3 Nov 2026 (RC 1.4 declared GO on 29 Oct, after slips from 20 Oct); the release upgrade changes systemd 259 to 262, dracut 108 to 111, grub2 2.12-66 to -81, rpm to 6.1 with signature checking enforced (`%_pkgverify_level=all`: third-party repos must ship verifiable signatures or be set gpgcheck=0 per repo), while the kernel series (7.2.11), dnf5 (5.4.6) and snapper (0.13.0) stay. Official path is system-upgrade, tested over at most 2 releases; support ends 4 weeks after N+2 (this PC: SUPPORT_END 2027-05-19, "the first day on which support is not provided"). https://www.mail-archive.com/devel@lists.fedoraproject.org/msg215972.html https://www.fedoraproject.org/wiki/Changes/Enforcing_signature_checking_by_default https://docs.fedoraproject.org/id/releases/lifecycle/ https://docs.fedoraproject.org/el/quick-docs/upgrading-fedora-offline/
14. Known upgrade breakers are third-party-package shaped. Fedora's own Common Issues list wine file conflicts blocking F42 to F43, akmods not rebuilt at the end of system-upgrade, and F44 breaking older Nvidia GPUs; the official guide says --allowerasing removals often hit third-party repo packages. So `system-upgrade download` (resolve and download, no change) is the pre-flight, its removal list is parsed, and hold-the-culprit is the answer. https://discussion.fedoraproject.org/c/ask/common-issues/82 https://discussion.fedoraproject.org/t/systems-with-wine-installed-cannot-be-upgraded-to-fedora-43/170296

### Batch 2: what matters for the design
- Separate /boot is the hole in every classic-Btrfs rollback: root snapshots exclude it, so a rollback pairs old /lib/modules with a newer kernel, or the old kernel was already pruned, and boot lands in emergency mode (Fedora, Arch and openSUSE users all hit it). Copy-able: move /boot into the Btrfs root (ESP alone outside; grub-btrfs reads each snapshot's own /boot; Fedora's Btrfs change page names this route), or rsync /boot into the root before and after every kernel transaction and restore it with the snapshot, and keep kernel retention at least as long as snapshot retention. https://discussion.fedoraproject.org/t/snapper-and-kernel-mismatch/190199 ; https://wiki.archlinux.org/title/System_backup ; https://fedoraproject.org/wiki/Changes/BtrfsByDefault
- Do not build rollback on `snapper rollback`: Fedora mounts root by name (`subvol=root`), so changing the default subvolume is a no-op, and upstream closed both fix attempts (PR 1184 on 2026-10-26, after a Fedora 44 test showed data stranded in root.rollback.N and /boot left behind). Own the switch: boot entries with explicit rootflags/subvolid, or RENAME_EXCHANGE of two subvolumes, and design for non-recursive snapshots (nested subvolumes stay behind). https://github.com/openSUSE/snapper/pull/1184 ; https://btrfs.readthedocs.io/en/latest/Subvolumes.html
- Decide the state split on purpose: SUSE excludes /var, /home, /opt, /srv, /tmp, /usr/local and bootloader dirs from rollback; the rpmdb lives in /usr/lib/sysimage/rpm so it rolls back with the packages; Arch insists the package DB stays on the root subvolume; Fedora's default puts /var inside root, so a rollback would rewind logs, databases and containers. Carve data-like /var into its own subvolumes, keep rpmdb and dnf history in root, and accept that newer data formats may not open after rollback. https://documentation.suse.com/sles/15-SP6/html/SLES-all/cha-snapper.html ; https://forums.opensuse.org/t/rolling-back-bad-update-when-var-is-separate-partition/185577
- Auto-rollback only inside a probation window, then stop: Apertis rolls back only while an upgrade is in progress, never after a version booted OK, and blacklists the failed update so it cannot loop until a newer one exists; FCOS, bootc and Universal Blue updaters skip the reverted version but take newer ones, and bootc warns a live timer can undo a manual rollback. For us: record the failed package set, hold it (versionlock), retry only on newer versions, and pause auto-retry during manual rollback. https://www.apertis.org/concepts/platform/system-updates-and-rollback/system-updates-and-rollback.pdf ; https://www.mankier.com/8/bootc-rollback
- Define "healthy" late and end to end, because "it booted" is a weak signal: systemd's own example marks success one minute after login and first program; health-checker only checks what a plugin covers (a failed k3s did not roll back); ChromeOS counts "updater launched", Ubuntu Core "snapd started"; RAUC and Torizon say hangs need a hardware watchdog plus panic-reboot. Our check: greetd up, dwl session reached, bar and notification daemons alive, network, then N seconds, with the watchdog armed only during probation. https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/ ; https://github.com/openSUSE/health-checker/issues/25 ; https://rauc.readthedocs.io/en/latest/basic.html
- The bootloader, ESP and shim are where "atomic" systems still fail: SUSE cannot roll the bootloader back, bootupd admits a buggy new bootloader is unhandled and BIOS updates are unsafe on power loss, Bluefin's bad shim signature stopped boot inside GRUB before any health check could run, an openSUSE user's 260 MiB ESP was suspected too small for a new initrd, NixOS /boot filled. So: grub/shim updates are a separate, last, opt-in step; the previous BLS entry, kernel and initramfs stay untouched until the new boot is blessed; pre-flight /boot and ESP free space; verify entry and initrd exist before reboot. https://github.com/coreos/bootupd ; https://universal-blue.discourse.group/t/bluefin-no-longer-boots-after-update-bad-shim-signature/2373 ; https://discourse.nixos.org/t/no-space-left-on-boot/24019
- Fedora's GRUB already ships boot counting (08_fallback_counting with grubenv boot_counter/boot_success) but it is OSTree-shaped: at 0 or -1 it sets `default=1`, meaning "entry 1 is the rollback deployment"; on a classic system entry 1 is merely the previous kernel, not a snapshot. Options: an Ubuntu-Core-style try/trying flag in grubenv (bootloader flips to trying; if the next boot still sees trying, fall back to the known-good entry) or systemd's +LEFT-DONE scheme (needs bootloader support and LoaderBootCountPath). Either way a hang is only caught if a watchdog forces the reboot. https://git.almalinux.org/rpms/grub2/commit/62a05cdcd46717732b142d43bb77fb8c79e5433c ; https://forum.snapcraft.io/t/ubuntu-core-boot-modes/5464 ; https://www.freedesktop.org/software/systemd/man/latest/systemd-bless-boot.service.html
- Run the transaction offline when possible: the systemd offline-update pattern (download first, reboot to system-update.target, snapshot, apply, delete the trigger early, FailureAction=reboot) avoids swapping libraries under a running desktop, the failure behind the Ubuntu 24.04 needrestart outage and Debian's "dpkg is not atomic" warning. One button can drive snapshot, download and test, reboot, apply, reboot, health check, bless; MicroOS cuts the cost with soft-reboot/kexec where only userspace changed. https://www.freedesktop.org/software/systemd/man/latest/systemd.offline-updates.html ; https://discourse.ubuntu.com/t/ubuntu-24-04-unattended-upgrades-failed-to-restart-nginx/67909 ; https://documentation.suse.com/sle-micro/6.1/html/Micro-transactional-updates/transactional-updates.html
- Make the updater a resumable state machine with a safe abort from every half-state: unattended-upgrades uses MinimalSteps and AutoFixInterruptedDpkg, sysupdate clears interrupted downloads and orders the boot entry last, transactional-update deletes failed snapshots, OSTree leaves a /boot stamp when finalization fails (yet may reboot into the same deployment, confusingly), and snapd's stuck refresh deadlocked revert against enable/remove. Persist a journal of the phase, make every step idempotent, and test kill-at-each-phase in the VM. https://github.com/mvo5/unattended-upgrades ; https://www.freedesktop.org/software/systemd/man/latest/sysupdate.d.html ; https://forum.snapcraft.io/t/how-to-recover-from-a-stuck-auto-refresh-upgrade/25235
- Space is a first-class failure mode: snapper's number limits (50 normal, 10 important) and space limits (50% max, 20% free, the latter needing qgroups) must be tuned; Bazzite wants at least 3% free; a 511 MB NixOS /boot with about 100 generations broke initrd copying (configurationLimit fixes it); Launchpad 1054927 shows automatic updates filling a default /boot until the updater crashed; Android Virtual A/B budgets 2.1-3.8 GB transient. Pre-flight free space on /, qgroup and /boot, cap kernels, auto-delete failed snapshots, and keep the pre-update snapshot `important` until blessed. https://github.com/openSUSE/snapper/blob/master/doc/snapper-configs.xml.in ; https://lists.snapcraft.io/archives/foundations-bugs/2016-May/284669.html ; https://source.android.com/docs/core/ota/virtual_ab
- Booting snapshots from grub-btrfs on Fedora is fragile and must be proven in the VM: open issues show the `root` subvolume layout missing rootflags (336), a hang before GNOME login on read-only snapshots (324), no submenu (348), path detection failing on Fedora 43 (419); read-only boots need the overlayfs hook (dracut 109 or a patched module) or writable snapshots, and Arch notes services needing writable /var fail. Prefer writable snapshot copies or overlay for the boot-menu rescue entry, and test the greetd/dwl session from it. https://github.com/Antynea/grub-btrfs/issues/336 ; https://github.com/Antynea/grub-btrfs/issues/324 ; https://github.com/Antynea/grub-btrfs/blob/master/initramfs/readme.md
- "Hold the culprit" has precedents: apt-listbugs pins offenders at priority 30000 and a daily job unpins once fixed (pins only apply after re-running apt); Arch bans partial upgrades (snap-pac: undoing a -Syu leaves the DB newer, so the next install is partial) and keeps a daily repo archive for date-pinned restores; Arch also warns that purging cached old versions blocks downgrades. For dnf: keep the pre-update RPM set and metadata until blessed, treat IgnorePkg-style skips as unsupported partial states, and bisect forward from the snapshot with versionlock rather than backward. https://manpages.debian.org/unstable/apt-listbugs/apt-listbugs.1.en.html ; https://barnettphd.com/snap-pac/ ; https://wiki.archlinux.org/title/Pacman
- Release upgrades are a different path from routine updates: FCOS update barriers force intermediate hops, stable only gets changes after time in testing, components are tested for upgrades not downgrades, and NixOS warns a database-schema upgrade cannot be undone easily; Pop!_OS offers an offline-systemd or recovery-partition route plus a post-upgrade repair step. For F44 to F45: one hop at a time, a dry-run and VM pre-flight first, a settling delay after release, and a repair pass (fstab, repos) after. https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/update-streams.adoc ; https://github.com/coreos/fedora-coreos-docs/blob/main/modules/ROOT/pages/update-barrier-signing-keys.adoc ; https://github.com/pop-os/upgrade
- Rollback must be one visible action that sticks: SteamOS has A/B yet users cannot roll back without manual partition switching; Bazzite's GRUB ostree:1 entry does not persist unless made primary; Guix roll-back skips service reload and activation; bootc rollback drops later /etc edits; Bazzite keeps only two deployments so a known-good one must be pinned. Ours should set the default entry persistently, restore /boot, re-arm the hold list, and be tested as rollback-of-rollback and rollback-while-pinned. https://github.com/ValveSoftware/SteamOS/issues/3018 ; https://docs.bazzite.gg/Installing_and_Managing_Software/Updates_Rollbacks_and_Rebasing/rolling_back_system_updates/ ; https://debbugs.gnu.org/db/37/37596.html
- Prefer boring, maintained building blocks and expect specialist updaters to churn: Clear Linux swupd was archived in August 2025, ABRoot v2 is "still in development" and its apply broke on kernel 7.2.11 (missing System.map), ParticleOS and GNOME OS promise no compatibility, greenboot's shell version is deprecated, and snapper's rollback for Fedora layouts was rejected. Build on dnf5, Btrfs, snapper for snapshots and cleanup only, GRUB/BLS and a small, VM-tested script of our own; pin versions. https://github.com/clearlinux/swupd-client ; https://github.com/Vanilla-OS/ABRoot/issues/504 ; https://github.com/fedora-iot/greenboot

### Batch 3: failure modes seen
- **Offline-update trigger silently returns to the old release.** dnf5-offline-transaction.service is skipped on an unmet `ConditionPathExists=/system-update` (seen with a Btrfs subvolume root and a dangling symlink); a stale prepared transaction from another updater is a second cause. Reported on F43 to F44 in 2026 (other dnf5 offline regressions hit F40 to F41); upstream dropped the condition only in Aug 2026 and the shipping release is unknown. Damage: no upgrade, no error, the user believes the system is current. Countermeasure: after the reboot check os-release, the offline state file and the unit's journal and report "upgrade did not run"; `dnf offline clean` before preparing; allow no other updater to prepare transactions. URLs: https://github.com/rpm-software-management/dnf5/issues/2773 https://discussion.fedoraproject.org/t/failed-offline-upgrade-from-f43-f44/193289 https://bugzilla.redhat.com/show_bug.cgi?id=2467655
- **Stored/offline transaction cannot be resolved.** Obsoleted or orphaned packages from old releases (KDE4 leftovers, wine i686 multilib), mixed F43/F44 state, and a dnf5 parser bug that skipped removals. Recurs across release upgrades in the forums (F40 to F41, F42 to F44, F43 to F44). Damage: reboot into the old release, or a half-upgraded mix that complicates rollback. Countermeasure: preflight in the VM and with a `--releasever=N` dry run (`--assumeno`), `repoquery --unsatisfied`; remove known-conflict packages first; allow `--allowerasing` only after reviewing the erase list. URLs: https://bugzilla.redhat.com/show_bug.cgi?id=2322527 https://discussion.fedoraproject.org/t/upgrade-from-fedora-42-44-isnt-working/192306 https://discussion.fedoraproject.org/t/failed-offline-upgrade-from-f43-f44/193289
- **Success reported as failure, and plugin ABI skew.** dnf5 calls reboot and races systemd's SIGTERM so the service exits 1 after a good upgrade; a new libdnf5 plugin is loaded into a process still running the old libdnf5. Both seen in 2026; PR #2916 (Oct 2026) fixes the exit race, the plugin skew (new interface in libdnf5 5.4.4.0) is open. Damage: spurious "failed" and a needless rollback; PackageKit records a failed update. Countermeasure: judge success from facts (rpm -q of key packages, os-release, offline state) not exit code; update the dnf5/libdnf5 stack in its own transaction first; reboot from the wrapper after dnf exits. URLs: https://github.com/rpm-software-management/dnf5/issues/2896 https://github.com/rpm-software-management/dnf5/issues/2959
- **Competing updaters, RPM lock, blocked reboot.** GNOME Software/PackageKit/dnf5daemon prepare their own offline updates and hold the RPM lock (dnf5 does not wait for it); a stale prepared update survives a normal update; terminal logout inhibitors deny `dnf5 offline reboot`. Several 2025-2026 reports, fixed in pieces (dnf5 5.4.3.0) with the lock wait still missing. Damage: failed `dnf install`, stale updates applied at shutdown, an update staged but never applied. Countermeasure: no software center on this desktop; our own flock with retry and timeout; `dnf offline clean` first; check logind inhibitors before the reboot step. URLs: https://github.com/rpm-software-management/dnf5/issues/2435 https://bugzilla.redhat.com/show_bug.cgi?id=2467655 https://discussion.fedoraproject.org/t/fedora-44-ws-and-block-on-sudo-dnf5-offline-reboot/189908
- **/boot or ESP out of space.** A /boot of 1 GiB or less (firmware growth), a 100 MiB ESP filled by stale kernel-install directories, an ESP too small for fwupd capsules. Common on older installs; F43 raised the default /boot to 2 GiB. Damage: kernel or initramfs missing or truncated, often silently because scriptlet failures are not shown. Countermeasure: preflight free space on /boot and /boot/efi, `installonly_limit=2`, drop the rescue kernel, clear stale ESP directories, and after the transaction verify vmlinuz and initramfs exist and look complete. URLs: https://discussion.fedoraproject.org/t/systems-with-1-gb-boot-partition-may-see-need-more-space-error-during-system-update/170285 https://discussion.fedoraproject.org/t/new-kernels-not-being-installed-in-boot-anymore/154050 https://bugzilla.redhat.com/show_bug.cgi?id=1252449 https://www.github.com/fwupd/fwupd/wiki/LVFS-Triaged-Issue:-ESP-too-small
- **initramfs content regressions.** A dracut/systemd change drops libcryptsetup; amdgpu firmware only takes effect after the initramfs is rebuilt. Seems to recur a few times a year and was fixed within days to a week in both 2026 cases (dracut-109-2 three days after the Rawhide regression). Damage: new kernel unbootable or no display. Countermeasure: keep an older kernel entry, inspect the new initramfs with `lsinitrd` (btrfs, amdgpu firmware), rebuild initramfs after linux-firmware/dracut updates, boot-once the new kernel with automatic fallback. URLs: https://bugzilla.redhat.com/show_bug.cgi?id=2481748 https://github.com/dracut-ng/dracut-ng/issues/2458 https://bugzilla.redhat.com/show_bug.cgi?id=2532853
- **BLS entries without root= or rootflags.** grub2-mkconfig/grubby/kernel-install interplay: a new kernel entry lacked root=; grub2-mkconfig can overwrite BLS snippets and drop rootflags=subvol. Sporadic (F43 report, Fedora Btrfs project notes). Damage: the new kernel times out waiting for the root device, emergency mode. Countermeasure: after kernel-install validate every /boot/loader/entries/*.conf for root= and rootflags; repair with `grubby --args`; avoid grub2-mkconfig after default-subvolume changes. - **Rollback with /boot outside Btrfs.** Kernel, initramfs and modules mismatch; /boot keeps only the three newest kernels; moving /boot onto Btrfs breaks grubenv writes. Structural: happens whenever a snapshot older than the latest kernel update is restored (reported on F44 in 2026). Damage: emergency mode, an unbootable rolled-back root. Countermeasure: refuse rollback unless modules for a bootable kernel entry exist, run `dracut --regenerate-all --force` or kernel-install afterwards, keep at least two kernels, copy /boot content beside each root snapshot. Countermeasure: cap entries (GRUB_BTRFS_LIMIT), shorten titles, keep grub-btrfs.cfg outside the rolled-back subvolume, regenerate and test the GRUB menu in the VM after every change. Structural since dnf5 became the default. Damage: an update runs without a snapshot, the wrong hold set, or a package silently swapped for another repo's build. Countermeasure: take the snapshot in our own wrapper and abort on failure, use `raise_error=1` for any hook, exact-NEVRA versionlock verified with `versionlock list`, set allow_vendor_change=false. Rare but each case is severe. Damage: broken package set or unbootable root. ### Batch 4: why updaters fail people

- **/boot lives outside the snapshot.** A rolled-back root meets a newer kernel, initramfs or BLS entry (or lost the kernel it needs because old ones were pruned) → emergency mode, stale GRUB entries; Timeshift, snapper and Btrfs Assistant all hit it. Countermeasure: make root plus /boot (kernel, initramfs, BLS entry of every retained snapshot) one rollback unit, either /boot inside the root subvolume or a per-snapshot copy; refuse rollback unless /lib/modules/<kver> and vmlinuz+initramfs match for at least one entry; after rollback run kernel-install and dracut for the restored kernel set, delete stale entries; never prune kernels a retained snapshot needs. ### Batch 5: what matters for the design

- **Unsafe today, 1: the swap is two renames.** `system/kawa-snap` lines 187-188 run `mv root root.swap; mv root.new root`; between them no `root` exists, and the kernel mounts by name (`rootflags=subvol=root`), so a cut there ends in dracut's emergency shell (btrfs-patrol hit exactly this on a double Ctrl-C). Use ONE `exch "$top/root" "$top/root.new"` (RENAME_EXCHANGE: atomic, legal between two subvolumes under any parents; `exch` from util-linux 2.41.5 is installed), then rename the old root to `root.old`, then `btrfs filesystem sync "$top"` before any /boot edit and before telling him to restart: RENAME_EXCHANGE only ends the in-memory transaction and Btrfs commits every 30 s, while /boot (XFS) commits on its own, so a cut can leave /boot matched to a root that never switched. Sources: https://man7.org/linux/man-pages/man2/rename.2.html https://man7.org/linux/man-pages/man1/exch.1.html https://android-kvm.googlesource.com/linux/+/3f79f6f6247c83f448c8026c3ee16d4636ef8d4f https://github.com/openSUSE/snapper/pull/1184 https://github.com/rocketman-code/atomic-rollback https://discussion.fedoraproject.org/t/btrfs-patrol-snapshots-before-every-dnf-transaction-and-one-command-rollback-on-fedoras-default-btrfs-layout/202145 https://btrfs.readthedocs.io/en/latest/ch-mount-options.html https://btrfs.readthedocs.io/en/latest/btrfs-filesystem.html https://man7.org/linux/man-pages/man2/syncfs.2.html
- **Unsafe today, 2: nested subvolumes are moved before the swap and leftovers are deleted with `-R`.** kawa-snap moves `.snapshots` (and every nested subvolume) INTO `root.new` (lines 176-185) before the swap, and its start-up cleanup (lines 149-151), its `undo` (line 153, reached from line 187) and line 189 all run `btrfs subvolume delete -R`, which is recursive and "not atomic". A cut, a failed rename at line 187, or a failed line 188 leaves every snapshot inside `root.new`, and the next run (or `undo`) deletes them. Rules: never `-R` a subvolume that still holds one (check `btrfs subvolume list -o` first); better, make `.snapshots` a top-level fstab-mounted subvolume (bullet 6) so nothing has to move; a snapper reviewer called the move-across code "already complex and not really atomic", and the proposed snapper design refuses a rollback when nested subvolumes hold data. Sources: https://btrfs.readthedocs.io/en/latest/btrfs-subvolume.html https://github.com/openSUSE/snapper/pull/1184 https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://github.com/jccl1706/btrfs-patrol
- **Unsafe today, 3: kernel and root are paired by two unrelated writes.** `kernel-install add` in the copy makes the added kernel the default (20-grub.install sets tmp_saved_entry, 95-set-boot-entry.install turns it into saved_entry after an initramfs check; `/etc/sysconfig/kernel` has UPDATEDEFAULT=yes, which `grub2-get-kernel-settings` turns into GRUB_UPDATE_DEFAULT_KERNEL=true) and kawa-snap runs it BEFORE the swap (lines 169-174), then sets the default again AFTER it (line 200, grubby). A cut before the swap boots the restored kernel on the unrestored root, a cut between the swap and line 200 boots the old default on the restored root; either way the kernel finds no `/usr/lib/modules/<its version>` (grub-btrfs has the same blind spot: no module check; on Fedora's default layout users are told to pick an older kernel by hand after a restore). Fix: run the chroot `kernel-install add` with UPDATEDEFAULT=no (or save and restore saved_entry), exchange, sync, flip the default exactly once; and make BOTH orders survivable: (i) reflink-copy each root's `/usr/lib/modules/<other KVER>` into the other so any kernel in /boot finds modules (an unowned directory that rpm overwrites later; unproven, test in the VM), or (ii) per-snapshot BLS entries carrying `rootflags=subvol=…` as sdbootutil does, where "switch" is one grubenv write. Prove with a VM power-cut matrix (cut after every line of restore). Sources: https://gitlab.com/redhat/centos-stream/rpms/grub2/-/raw/c10s/20-grub.install https://gitlab.com/redhat/centos-stream/rpms/grub2/-/raw/c10s/95-set-boot-entry.install https://raw.githubusercontent.com/Antynea/grub-btrfs/master/41_snapshots-btrfs https://raw.githubusercontent.com/openSUSE/sdbootutil/main/sdbootutil https://discussion.fedoraproject.org/t/btrfs-restore-with-ext4-formatted-boot/77885 https://discussion.fedoraproject.org/t/btrfs-assistant-no-boot-option-for-snapshots/185284 https://bbs.archlinux.org/viewtopic.php?id=286308
- **The /home split (fedokawaii-split), exact procedure.** Run it offline from a unit wanted by `system-update.target` (or `rescue.target`): nothing holds /home open (btrfs-patrol: processes "keep writing to the old copy"); dnf5's own offline unit coexists because `_execute` exits 0 when its symlink is absent. Steps: mount the top level (`subvolid=5`); stop snapper timers and snapperd; refuse if a libvirt VM runs; `btrfs subvolume create top/home`; `cp -aT --reflink=always -x /home top/home` (-a keeps SELinux context and xattrs; -x should skip nested subvolumes, verify); `mv` the nested subvolumes Downloads and VM into `top/home/dia/` (a subvolume renames across parents; the VM images are NOCOW and cannot be reflinked into a COW directory); compare both trees (names, sizes, modes, owners, mtimes, `ls -Z`, a checksum sample); write the fstab line (`subvol=home`, same option string as `/`, never subvolid) through a temp file and rename, old fstab kept; `mount /home` OVER the old directory, with no rename of /home, so there is never a moment without a mount point; `restorecon -F` the new top directory only if `ls -Zd` differs; delete the shadowed copy after a good boot via a bind mount of `/` with plain `rm -rf` (never `subvolume delete -R`). Snapshots taken before the split hold a stale /home and an fstab without it: mark them non-restorable (or delete them) so a restore can never bring that /home back. Sources: https://github.com/jccl1706/btrfs-patrol https://btrfs.readthedocs.io/en/latest/Reflink.html https://man.archlinux.org/man/cp.1 https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://android-kvm.googlesource.com/linux/+/3f79f6f6247c83f448c8026c3ee16d4636ef8d4f https://libvirt.org/formatstorage.html https://man7.org/linux/man-pages/man7/systemd.offline-updates.7.html https://www.freedesktop.org/software/systemd/man/latest/systemd.special.html https://raw.githubusercontent.com/rpm-software-management/dnf5/main/dnf5/commands/offline/offline.cpp https://raw.githubusercontent.com/SELinuxProject/selinux/main/policycoreutils/setfiles/restorecon.8
- **Layout and fstab rules.** Flat top-level subvolumes mounted from fstab: `home`, `log` (/var/log), `fk` (/var/lib/fedokawaii-update), optionally cache, tmp, libvirt, containers. NEVER /var or /var/lib whole: `/var/lib/selinux` (policy store behind /etc/selinux), `/var/lib/alternatives`, `/var/lib/rpm-state`, `/var/lib/authselect` must roll back with /usr and /etc (Fedora moved the rpmdb to /usr in 36 for the same reason; btrfs-patrol: "think twice before making /var/lib one"). Prefer flat to nested: nested subvolumes show up as empty stubs in snapshots and a root swap has to carry them. systemd-tmpfiles creates nested subvolumes itself when a path is missing on btrfs (`Q /home`, `q /var/tmp`, `Q /var/lib/machines`, `Q /var/lib/portables` on this PC), so `/home` must be mounted before tmpfiles runs (fstab does that). fstab lines: `subvol=NAME` (subvolid cannot follow a rollback; btrfs-patrol refuses it), the identical option string everywhere (only the first mount's options take effect), no `nofail` on /home (a failed mount must stop the boot, not show an empty /home), `nofail` plus `x-systemd.device-timeout` is acceptable for log. Re-assert these lines in the incoming root's fstab before every exchange: they are machine state, not OS state, and an older snapshot would boot without them (SUSE: rollbacks are supported only while the preconfigured subvolumes stay). The installer ISO can build this layout from the first boot with kickstart `btrfs / --subvol --name=root` and `btrfs /home --subvol --name=home` style lines. grub-btrfs read-only snapshot boots (the boot menu's last resort) need /var/log or /var on its own subvolume, and on dracut an overlay (`rd.live.overlay.overlayfs=1`, a patched module before dracut 109; Fedora 44 has 108). - **Constrain the answer, not the thinking.** Use `response_format`/`json_schema` (GBNF) with `additionalProperties:false`, an enum verdict `fix|cannot_fix`, and string fields for file, search, replace and a short reason; repeat the schema in the prompt (the model never sees it); unsupported schema keywords are skipped silently, so validate with the converter or use llguidance, which errors. Strict formats hurt reasoning and distort the model's distribution, so use two stages: free reasoning under `--reasoning-budget` or a token cap, then the constrained final answer (llama.cpp's chat parser already applies a json_schema after the reasoning block); watch the budget flag, it regressed once. - **Edit format: exact SEARCH/REPLACE pairs (or the whole small file), applied strictly, with the diff computed by us.** Aider found simple, familiar, line-number-free, high-level edits cut lazy output (20% to 61%) and flexible patching cut errors 9x; for system configs prefer strict exact-match plus one retry that returns the apply error, since fuzzy application can touch the wrong lines. For whole-file rewrites `--spec-type ngram-mod` makes copying cheap; use low temperature or greedy (Devstral 0.15). - **Ground against hallucinated options, then check mechanically.** Feed the new version's man page or `--help`, the default config, the package changelog diff and the failing check output (Byam's best prompts: buggy line, API diff, error message), then reject any key in the proposed diff that does not appear in that documentation. Documentation alone is not enough (it helped some models and hurt others in the pwquality study) and many parsers silently ignore unknown keys, so a green check can be a fake fix. - **Verify-then-keep is necessary, not sufficient.** Keep a fix only if the originally failing check turns green, the full verify suite and the headless desktop smoke test pass, the diff is small and not deletion-only or "disable the feature" (deleting functionality passes validators), the verifier lives outside anything the model can write (reward hacking is common and "do not cheat" prompts barely help), invalid edits are rejected by a lint gate before applying (SWE-agent +3.0 points), and the change is reported plainly. STRATUS's transactional no-regression with undo is the pattern our snapshot rollback implements. - **Sandbox, zero tools, untrusted input.** The model gets no shell and no tools: text in, schema-bound JSON out (OWASP LLM06: minimise functionality, enforce authorization outside the LLM; the Replit agent ignored a written freeze and misreported rollback state, so trust only the verifier's view of state). Logs and changelogs are attacker-influenced text (LLM01): quote them as data and cap their size. - **Budgets and watchdogs.** At most two attempts, the second fed with the verifier's output (self-repair gains are modest and need external feedback; intrinsic self-correction can lower accuracy); wall-clock cap, `max_tokens`, `--reasoning-budget`; treat a Vulkan ErrorDeviceLost or ring timeout (issues 21724 and 27154) or a stalled server as "no fix": kill the unit, free VRAM, hold and tell. Prefill is cheap (a 7B-class model does about 2.8k t/s on this card) but verify with `-d`; avoid huge `-ub` at long depth.
