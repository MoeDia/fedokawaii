### Batch 1: what matters for the design

Tags: [X] contradicts one of our assumptions (a)-(e); [OK] confirms one; the rest are new facts the design must absorb.

1. [X b] With a separate /boot, grub-btrfs boots a snapshot with the live /boot's kernels, not the snapshot's. In `boot_separate` mode kernels, initramfs and microcode are globbed once from the live /boot and reused for every snapshot entry (`boot_bounded`, per-snapshot /boot, applies only when /boot is inside the same Btrfs subvolume); entries add `rootflags=subvol=<snapshot>`; no kernel found prints "Kernels not found." and exits 0. A snapshot boots only if /boot still holds a kernel whose /usr/lib/modules/KVER exists in that snapshot. https://github.com/Antynea/grub-btrfs/blob/master/41_snapshots-btrfs
2. [X a] A root rollback does NOT keep /boot's kernels usable with installonly_limit=2. dnf5 keeps the 2 newest kernels (default 3, minimum 2; this PC sets 2 in /etc/dnf/libdnf5.conf.d/90-fedokawaii.conf) and kernel removal deletes their /boot files; a snapshot two or more kernel updates old then has no matching vmlinuz/initramfs on /boot (initramfs is built into /boot, never into a snapshot) and the newest kernel has no /usr/lib/modules/KVER in it. Every snapshot still carries /usr/lib/modules/KVER/vmlinuz (checked here), so the rollback step must run `kernel-install add KVER /usr/lib/modules/KVER/vmlinuz` (rebuilds BLS entry + initrd from the rolled-back root) before first boot, or kernel retention must follow snapshot retention. https://dnf5.readthedocs.io/en/latest/dnf5.conf.5.html https://www.freedesktop.org/software/systemd/man/latest/kernel-install.html
3. [X b] Read-only snapshot boot depends on a dracut hook that changes at exactly the release we are about to take. grub-btrfs needs /var (or /var/log) on its own subvolume or its overlayfs initramfs module; dracut < 109 has an overlayfs mount bug needing a hand-patched copy of module 70overlayfs (this PC: dracut 108-8, unless Fedora backported the fix: test in the VM); dracut 110 renamed `rd.live.overlay.*` to `rd.overlay.*` and F45 ships 111-4. Safer than the hook: boot a read-write clone of the chosen read-only snapshot. https://github.com/Antynea/grub-btrfs/blob/master/initramfs/readme.md https://github.com/dracut-ng/dracut-ng/blob/main/man/dracut.cmdline.7.adoc https://packages.fedoraproject.org/pkgs/dracut/dracut/fedora-45.html
4. [X, rollback mechanism] `snapper rollback` cannot work on this layout. It "creates two new snapshots and sets the default subvolume", and btrfs `set-default` "takes action on next mount"; but this PC pins root twice (`subvol=root` in fstab and `rootflags=subvol=root` on the kernel command line), and /.snapshots sits inside `root` (not a separate mount; snapper makes it a nested subvolume, and snapshots do not carry nested subvolumes). A rollback needs our own swap: a new read-write snapshot named in `rootflags=`/BLS options, with .snapshots moved to a top-level subvolume mounted at /.snapshots (the @/.snapshots layout snapper's health check expects). https://manpages.opensuse.org/Tumbleweed/snapper/snapper.8.en.html https://btrfs.readthedocs.io/en/latest/btrfs-subvolume.html https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://doc.opensuse.org/documentation/tumbleweed/snapper/
5. [OK c, with limits] dnf5 5.4.6 (identical in F45) has versionlock (/etc/dnf/versionlock.toml; name globs plus epoch/evr/arch conditions) and offline/system-upgrade built in; both ship with the dnf5 package set on this PC. History undo/rollback exist but do not promise old packages; only exit codes 0/1/2 are documented (check-upgrade adds 100); `upgrade` lost --skip-broken and unmatched specs now fail; `tsflags=test`, `--downloadonly`, `--store` and `system-upgrade download` are the no-change pre-flights; 5.4.3.0 was published as "broken - do not use", so pin the dnf5 build too. https://dnf5.readthedocs.io/en/latest/commands/versionlock.8.html https://dnf5.readthedocs.io/en/latest/dnf5.8.html https://github.com/rpm-software-management/dnf5/releases
6. Offline-upgrade mechanics. Its state lives in /usr/lib/sysimage/libdnf5/offline, inside the root subvolume, so a rollback restores whichever offline state the snapshot had: run `dnf5 offline clean` after any rollback. The installed unit has `Requires=sysinit.target dbus.socket` and `OnFailure=` a cleanup that deletes /system-update and reboots, matching systemd's rules (remove the flag early, always reboot, "revert to the old file system snapshot"); so a failed offline upgrade lands back in the old system and success must be judged by the resulting release, not by the absence of an error. https://www.freedesktop.org/software/systemd/man/latest/systemd.offline-updates.html https://dnf5.readthedocs.io/en/latest/commands/offline.8.html
7. [X d, partly] Fedora's grub2 has boot counting, but it is a kernel fallback, not a snapshot rollback. `08_fallback_counting` counts `boot_counter` down only while it is set and `boot_success=0`, and at 0/-1 sets `default=1` (the second entry: the next-older BLS kernel; on ostree "the rollback deployment"); `10_reset_boot_success` sets boot_success=0 on every boot, so userspace must set `boot_success=1` (Fedora: the user timer grub-boot-success.timer, 2 min into a session, via grub2-set-bootflag) and `boot_counter=N` ("both ... need to be set from userspace"); offline updates bump boot_indeterminate. GRUB's `fallback` fires only when commands of the chosen entry fail, not on OS-level failure. We need a system-level confirm unit ordered before boot-complete.target plus our own grub.d snippet to select a snapshot entry; grubenv is fine on our XFS /boot, whereas Fedora's Cloud change avoids grubenv features on a Btrfs /boot. https://github.com/rhboot/grub2/blob/fedora-46/util/grub.d/08_fallback_counting.in https://github.com/rhboot/grub2/blob/fedora-46/util/grub.d/10_reset_boot_success.in https://www.fedoraproject.org/wiki/Changes/CleanupGnomeHiddenBootMenuIntegration https://www.gnu.org/savannah-checkouts/gnu/grub/manual/grub/grub.html

Boot assessment elsewhere is not directly reusable. systemd's Automatic Boot Assessment is BLS-file-rename counting inside systemd-boot (GRUB is not mentioned; bless-boot needs the LoaderBootCountPath EFI variable); systemd-boot-check-no-failures only tests "no failed units" and is disabled by default; greenboot(-rs) gives the pattern (required.d/wanted.d checks before boot-complete.target, red.d/green.d, max attempts) but rolls back only through rpm-ostree/bootc. Reuse the pattern (our verify as a unit ordered before boot-complete.target), not the tools. https://systemd.io/AUTOMATIC_BOOT_ASSESSMENT/ https://www.freedesktop.org/software/systemd/man/latest/systemd-boot-check-no-failures.service.html https://github.com/fedora-iot/greenboot-rs
9. [X e, consequence] /home inside the root subvolume is rolled back with it, and so is /var (the persistent journal, capped at 500M here, and the logs of the failed attempt) plus everything under /home/dia except the nested Downloads and VM subvolumes: dotfiles, ~/repos and the .claude notes revert to the snapshot's state. Btrfs docs: give data that must survive rollbacks its own subvolume; Fedora's default layout has separate root and home subvolumes; openSUSE keeps /home out of snapshots. Before rollback ships, /home (and /var/log) must become their own subvolumes, and the update report must be copied out before any rollback. https://btrfs.readthedocs.io/en/latest/Subvolumes.html https://fedoraproject.org/wiki/Changes/BtrfsByDefault https://doc.opensuse.org/documentation/tumbleweed/snapper/
10. Snapshot space is not managed by default. Snapper's defaults do no cleanup (NUMBER_CLEANUP=no, timeline off; NUMBER_LIMIT 50, important 10 counted separately); SPACE_LIMIT 0.5 / FREE_LIMIT 0.2 need quotas, and qgroups slow commits as snapshots multiply (squota, kernel 6.7 or newer, avoids shared/exclusive tracking). Metadata exhaustion gives ENOSPC while data space is free (deletion still works; balance needs workspace; start with `-dusage=0`); deleted snapshots free space asynchronously (`btrfs subvolume sync`, `delete -c`). The pre-flight must read `btrfs filesystem usage`, not df. https://manpages.opensuse.org/Tumbleweed/snapper/snapper-configs.5.en.html https://btrfs.readthedocs.io/en/latest/Qgroups.html https://btrfs.readthedocs.io/en/latest/trouble-index.html https://btrfs.readthedocs.io/en/latest/btrfs-filesystem.html
11. RPM gives no all-or-nothing transaction, so the snapshot is the only undo. A failing %pre stops only its package, any non-zero scriptlet turns the result into an error while the transaction goes on, and rpm.8 has no rollback option; the sqlite rpmdb at /usr/lib/sysimage/rpm survives a killed transaction and sits inside the snapshot, consistent with /usr; verify with `rpm -Va`, repair with `rpmdb --rebuilddb`; the rpm and libdnf5 systemd-inhibit plugins block shutdown during a transaction (a pulled plug still needs the snapshot). https://rpm.org/docs/latest/man/rpm-scriptlets.7 https://rpm.org/docs/latest/man/rpmdb.8 https://fedoraproject.org/wiki/Changes/Sqlite_Rpmdb https://rpm.org/docs/latest/man/rpm-plugin-systemd-inhibit.8
12. Bootloader files are outside every snapshot, and are about to move. The ESP (vfat) and /boot (XFS) are not Btrfs, so a root rollback never touches BLS entries, initramfs, grubenv or the shim/grub binaries; F44's BootLoaderUpdatesPhase1 stages shim/grub2 under /usr/lib/<pkg>/<arch> and copies them out in a posttrans step whose mechanism is still undefined (bootupd is the candidate), so after a rollback /usr may hold older bootloader files than the ESP: re-sync or tolerate. https://fedoraproject.org/wiki/Changes/BootLoaderUpdatesPhase1 https://packages.fedoraproject.org/pkgs/grub2/grub2-common/fedora-45.html
